# Autonomous work queue

The **only** source of work for an unattended loop session (`docs/playbooks/autonomous-loop.md`).
The loop does not decide what to do — it works this list, top to bottom, one item at a time, and
stops the moment it reaches an item marked `HALT` or runs out of items.

Each item declares the files it may touch (nothing outside that scope, ever) and a done
criterion a script can check without judgment. `scripts/autonomous_gate.py` is what actually
evaluates "done" — this file is the plan, that script is the referee.

Spec: `docs/specs/SPEC-001-vertical-slice-account-prioritization/`. Design already resolved in
that spec's `plan.md` and in `docs/decisions/ADR-0002-persistence-layer.md` — the loop implements
it, it does not re-derive it. **Read ADR-0002 before starting Item 1** — it explains why
`agent_actions.run_id` is nullable, why the LangGraph checkpoint tables must never appear in an
autogenerated migration, and why `SqlAlchemyUnitOfWork` shares one session instead of changing
`DecideApproval`'s signature.

The Alembic scaffolding (`alembic.ini`, `migrations/env.py`, `migrations/script.py.mako`) and the
`Base` declarative class (`packages/core/revops/infrastructure/persistence/models.py`) already
exist, committed and verified (`alembic current` and `alembic revision --autogenerate` both run
clean against the docker-compose Postgres). Do not recreate them. `env.py` already:
- reads `DATABASE_URL` from the environment (falls back to the local docker-compose default),
- sets `WindowsSelectorEventLoopPolicy` before running async migrations (psycopg's async driver
  cannot use Windows' default `ProactorEventLoop` — this bit twice already; if you write any new
  standalone async entry point that touches Postgres, it needs the same guard),
- excludes the LangGraph checkpoint tables from autogenerate via `include_name` — **never remove
  or work around this filter**, even if autogenerate reports it wants to drop those tables. That is
  expected and correct; the tables are owned by `AsyncPostgresSaver.setup()`, not by this schema.

`tests/integration/conftest.py` already exists (`database_url`, `postgres_dsn` fixtures, and a
`_require_postgres` autouse fixture that fails loudly — not silently skips — when Postgres isn't
reachable). Reuse it; do not create a second one.

## Item 1 — SQLAlchemy models: all entities + audit tables

- **Scope:** `packages/core/revops/infrastructure/persistence/models.py`,
  `tests/unit/infrastructure/__init__.py`,
  `tests/unit/infrastructure/persistence/__init__.py`,
  `tests/unit/infrastructure/persistence/test_models.py`
- **What:** ten tables mapped as SQLAlchemy 2.0 declarative models (`Mapped[...]`,
  `mapped_column`) on the existing `Base`: `organizations`, `users`, `accounts`, `contacts`,
  `opportunities`, `interactions`, `tasks`, `agent_runs`, `agent_actions`, `approvals`.
  - The model follows the domain, never the reverse (`docs/playbooks/db-migration.md`): match the
    fields already fixed in `domain/entities/*.py` (all `@dataclass(slots=True)`). Value objects
    (`Score`, `RiskLevel`, `EmailAddress`, `CompanyDomain`) persist as their primitive value —
    reidration into the value object happens at the repository boundary (item 3), not here.
  - `agent_runs`, `agent_actions`, `approvals` are infrastructure tables with **no domain entity**
    (ADR-0002) — model them directly from `spec.md`'s "Data model impact" section and the columns
    that section and `AGENTS.md` actually require (`graph_version`, `prompt_version`, model config,
    latency, token cost on `agent_runs`; the usual audit fields on `agent_actions`/`approvals`).
  - **`agent_actions.run_id` is nullable** (ADR-0002 — there is no real `agent_run` to reference
    yet; do not make it `NOT NULL` and do not skip the column).
  - Indexes: `organization_id` on every tenant-scoped table; unique `accounts(domain)` per
    organization; unique `contacts(email)` per organization; foreign keys throughout.
  - Append-only tables (`agent_runs`, `agent_actions`, `approvals`): no column or constraint that
    enables an `ON UPDATE`, no cascade delete.
- **Done when:** gate green, plus `test_models.py` proves — without needing a database —
  that all ten tables exist in `Base.metadata.tables`, `agent_actions.run_id` is nullable, and the
  three audit tables carry no update-enabling construct.

## Item 2 — First Alembic migration

- **Scope:** `packages/core/revops/infrastructure/persistence/migrations/versions/`
- **Depends on:** item 1.
- **What:** `alembic revision --autogenerate -m "<message>"` against the running docker-compose
  Postgres, then **read the generated file line by line** before accepting it
  (`docs/playbooks/db-migration.md`: "Autogenerate misses constraint changes, index intent and
  data moves") — confirm indexes and the `agent_actions.run_id` nullability came through as
  intended, and confirm the LangGraph checkpoint tables do **not** appear (if they do, the
  `include_name` filter in `env.py` was bypassed or broken — stop and report, do not just delete
  those lines from the migration by hand).
- **Done when:** gate green, plus the round-trip actually run and its output captured as evidence:
  `alembic upgrade head && alembic downgrade -1 && alembic upgrade head` against the real database
  (`docker compose ps` must show `revops-postgres` healthy first).

## Item 3 — Repositories and `SqlAlchemyUnitOfWork`

- **Scope:** `packages/core/revops/infrastructure/persistence/repositories.py`,
  `packages/core/revops/infrastructure/persistence/unit_of_work.py`,
  `tests/unit/infrastructure/persistence/test_repositories.py`
- **Depends on:** items 1-2.
- **What:** implement `application/ports.py`'s Protocols structurally (do not inherit from
  them — follow the convention `tests/unit/application/test_ports.py` already establishes):
  - `SqlAlchemyAccountRepository` — `get`, `list_for_organization`, `list_interactions`,
    `list_open_opportunities`. Read-only by design; do not add write methods.
  - `SqlAlchemyTaskRepository` — `add`, `get`, `update`.
  - `SqlAlchemyAuditTrail` — `record`, writing to `agent_actions` with `run_id=None` (item 1's
    nullable column — this is expected, not a bug to work around).
  - `SqlAlchemyUnitOfWork` — exposes all three above sharing **one `AsyncSession`**
    (`__aenter__`/`__aexit__`/`commit`/`rollback`). Do not change `DecideApproval`'s constructor or
    call signature — the atomicity this closes is composed by whoever calls the use case, not by
    the use case itself (ADR-0002).
  - `organization_id` is filtered **inside** every read method, never left to the caller to
    remember (`spec.md` Security considerations, `AGENTS.md`).
  - All I/O is `async` (SQLAlchemy async engine/session), matching every port except `Clock.now`.
- **Done when:** gate green, plus unit tests proving each class satisfies its Protocol via
  `isinstance(..., SomePort)` (structural typing, no database needed for this check — mock or stub
  the session at this level, real-database behaviour is item 4's job).

## Item 4 — Integration tests against the docker Postgres

- **Scope:** `tests/integration/test_persistence_repositories.py`
- **Depends on:** items 1-3.
- **What:** exercise the real repositories against the real database (use the existing
  `tests/integration/conftest.py` fixtures — `database_url`/`postgres_dsn`, do not write a new
  conftest):
  - Each repository's methods round-tripped against real rows.
  - Each value object (`CompanyDomain`, `EmailAddress`, `Score`) round-tripped through the
    persistence boundary correctly.
  - A `Task`'s transitions (`mark_done`, `cancel`) persisted, and an illegal transition still
    raises `InvalidTransitionError` after a real save/reload cycle.
  - **The tenant-isolation test** (explicit `tasks.md` §3 item, and it is what proves acceptance
    criterion 10): seed two organizations, confirm a repository call scoped to one never returns or
    mutates the other's rows.
- **Done when:** gate green, `pytest tests/integration -q` passes for real against the running
  compose stack, and the isolation test specifically is named in the evidence written to
  `.handoff/STATE.md` — not just "integration tests pass."

## Item 5 — LangGraph node/checkpoint/interrupt wiring — **HALT: PLAN-MODE-REQUIRED**

- **Scope:** would touch `packages/core/revops/infrastructure/agent/` — do not create or edit
  anything here.
- **Why halted:** `spec.md`'s own words: *"LangGraph checkpoint persistence across a process
  restart is the riskiest technical unknown."* The mechanism itself is now proven (the
  checkpoint-restart spike, commit `1a8dad8`), but the graph's own design — state shape, thread
  identity, static vs. dynamic interrupt placement, who calls `DecideApproval` — is still open and
  still requires the user in Plan Mode, per `AGENTS.md`'s standing complexity-flagging rule.
- **On reaching this item:** stop. Do not write code toward it. Write the halt reason and the
  state of everything before it to `.handoff/STATE.md`, and end the session. The user resumes
  this item deliberately, in Opus + plan mode.

## Rules for the loop

- Work items in order. Do not skip ahead even if a later item looks easier or independent — the
  order encodes real dependencies (items 2-4 each need the ones before them).
- Never touch a file outside an item's declared scope. If finishing an item genuinely requires
  touching something outside scope, that is itself a signal to stop and flag it, not to expand
  scope silently.
- **Never call `EnterWorktree` for this project, in any mode — this is a hard rule, not a
  preference.** Found live (SPEC-001 persistence, 2026-08-29): `revops` resolves through a PEP 660
  editable install pinned to **absolute paths baked in at `pip install -e ".[dev]"` time**, in a
  global per-user site-packages, not a project `.venv`. A git worktree is a genuinely separate
  directory tree — `import revops...` inside it keeps silently resolving to the **main checkout's**
  files regardless of `cwd`. Every test, and the gate's own `pytest` run, would exercise stale code
  forever. Reinstalling editable from inside the worktree is not a fix either — it would rebind a
  shared, per-user Python environment away from the main checkout, breaking it and any other
  concurrent session the moment the worktree is removed. Real, reproduced incident:
  `.handoff/log/2026-08-29-*-claude.md`.
  **If launched with `--bg` and blocked by `bgIsolation: worktree`:** stop and report it — do not
  call `EnterWorktree` to work around the block. Unattended work on this repo must run as a plain
  foreground interactive session (no `--bg`) in the main checkout, where this isolation layer never
  activates.
- One commit per completed item, on that same branch, following the same commit and verification
  discipline as any other work in this repo (`AGENTS.md`).
- **Do not merge or reconcile the branch yourself.** That is a human/main-session step, done
  afterward — the loop's job ends at the last commit + a clean `STATE.md`.
- Tick the matching box in `docs/specs/SPEC-001-vertical-slice-account-prioritization/tasks.md`
  as each item completes.
- Update `.handoff/STATE.md` after every item — evidence, not claims, same as always.
- **Docker must be running** (`docker compose up -d`, confirm `docker compose ps` shows
  `revops-postgres` healthy) before item 2 — the migration round-trip needs it, and item 4 needs it
  throughout. If it isn't running and you cannot start it yourself, stop and report — do not skip
  the round-trip verification or the integration tests to work around a missing database.
